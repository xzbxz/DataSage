# 用户视角审查实例：26 题生产 E2E 回答

Worked example: 2026-08-07 对 `workspace/E2E_测试报告_26题.md` 的逐条用户视角审查。
用于对照"哪些回答业务用户会觉得好 / 哪些会抓狂"。

## 判定结论（26 条）

- 用户会觉得答得好（约 15 条）：表格清晰、结论先行、口径一句话讲清、
  主动给后续选项。代表：#5 Yoga 每月收款、#9 HCM 去年每月完成率、
  #15 上半年对比、#16 Jackie/Bill 对比、#8 k000265 风险、#24 按周出库、
  #22 越南语、#23 英语。
- 质量高但体验可更好（约 7 条）：免责声明过密、颗粒度不一致、
  "完成"与"实际等待澄清"标签误导。
- 真正让用户不满（2-3 条）：见下。

## 典型失败模式（每条都是可复用的检查点）

### 1. 实体解读死板：HCM-Emma 当客户查（#4）

用户问 "HCM-Emma2026年的收款情况"：
- 模型按"客户"实体精确匹配 → ENTITY_NOT_FOUND → 输出 5 行"找不到 + 候选0 +
  可能原因3条"的道歉。
- 业务语境里 "HCM-Emma" 更可能是 部门HCM + 业务员Emma（对比 #16 "HCM 的
  Jackie 和 Bill" 的写法）。
- 教训：`<DEPT>-<NAME>` 组合优先试 部门+业务员 解读，而不是当客户名。
- 用户的直觉：这种回答看 5 行就想划走——即使诚实，也没解决问题。

### 2. 别名归一化缺失 + 把数据问题推给用户（#25 #26）

用户问 "印尼上半年收款金额排名前二十的客户名单" → 空；追问 "帮我换成原币，
印尼盾" → 又空。模型两次都说"系统里可能不叫印尼/印尼盾，请确认准确叫法"。
- 用户视角：你想让我怎么确认？我又不知道系统里登记成什么。
- 根因：区域/币种别名没有归一化（印尼=印度尼西亚=IDN，印尼盾=IDR，
  曼谷=Bangkok），把系统数据质量问题变成了用户的责任。
- 教训：空结果时应先自己试常见别名，而不是让业务用户当字典。

### 3. 澄清选项给业务用户造成负担（#3 家纺）

"家纺客户/家纺部门/家纺产品"三个选项把分类学知识推给用户——用户只知道
"家纺团队"是约定俗成叫法，未必知道它在系统里属于哪类。
- 更好的做法：给默认（"先按家纺客户分类查，没有再试部门"），而不是列选项。

### 4. 多轮追问深度不对齐（#21 Jolie 出库明细）

#20 Agnes 昨天出库明细给了完整回答（总额+客户明细+负数说明），#21 "Jolie呢"
只有三行汇总数字。指代接上了，但颗粒度没对齐——用户期待同样的明细深度。

### 5. 同指标入口可用性矛盾（#7 vs #8 应收周转天数）

#7 问"公司整体应收周转天数"答"指标没有"（查 receivable 域 46 个指标无此指标）；
#8 客户 k000265 却算出 35.43 天（customer_risk 域 formal_receivable_turnover_days）。
- 技术解释：指标归档在 customer_risk 域（触发词：客户风险/DSO/结算速度），
  用户从"应收"入口问时模型不跨域搜索 → 诚实说没有。
- 用户视角：你们到底有没有这个数？——同指标不同入口可用性不一致会破坏信任。
- 详见 SKILL.md "Metric cross-domain discovery" 一节。

### 6. 免责声明过密（全报告 10+ 次）

"结果被截断不代表全量"出现 10+ 次，业务用户会觉得系统总给不全——
真实体验是"我要 Top20 你只给 Top10"。正确但要控制密度，或用更友好的表述。

### 7. 状态标签误导

#1/#14/#18 标记"✅ 完成"却实际经历了等待澄清（无人应答后模型自行选了一个
继续）。报告里的"完成"定义对用户有误导——应区分"一次完成"和"默认选择后完成"。
